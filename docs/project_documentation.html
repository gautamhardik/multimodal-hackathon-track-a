1Overview

Coronary Risk Explorer predicts overall coronary artery disease (CAD, the dataset's Cath label) and ≥ 50% stenosis of the LAD, LCX and RCA from 54 routine variables of one clinic visit: demographics, history, symptoms and examination, ECG, laboratory tests and echocardiography. Each estimate is calibrated, explained with exact SHAP values, and painted onto the matching coronary artery of a real anatomical 3D heart that users can rotate, zoom and select. The whole system is one web application with a FastAPI model service; inputs re-score in about 60 ms, so the heart and the explanations update while the user types.

2Data and preprocessing

Dataset. UCI Extension of Z-Alizadeh Sani: 303 patients referred for angiography at one centre; 59 columns. Targets: Cath (CAD prevalence 71%), and stenosis of LAD, LCX and RCA (stenotic = 1, normal = 0).

Audit (Notebook 1). No missing values, no exact or conflicting duplicate patients, no physiologically implausible values. One constant column (Exertional CP, all "N") was dropped, leaving 54 input features. A typo in Sex ("Fmale") was corrected. Strong collinearity (Neut–Lymph r = −0.92) was kept, since tree models tolerate it. A leakage audit confirmed that only the four target columns carry outcome information.

Encoding (Notebook 2). Binary string fields → 0/1; BBB (N/LBBB/RBBB) one-hot; numeric fields passed through for trees and standardised for linear models and SVMs. Valvular heart disease (VHD) was tested two ways: Config A ordinal (N < mild < moderate < severe; 56 transformed features) and Config B one-hot (59 features); the choice was made per target on development CV.

Leakage control. Every transformer lives inside an sklearn Pipeline, so it is fitted only on the training part of each fold. BMI and obesity are derived from weight and height at prediction time, exactly as in the data.

Validation design

  • Split: 242 development / 61 holdout patients (stratified on Cath, seed 42). The holdout indices are written to preprocessing_config.json and the holdout stayed sealed until Notebook 6, where the frozen models were scored exactly once. No model, feature, hyperparameter or threshold decision used it.
  • Development CV: repeated stratified 5-fold × 5 repeats (25 folds), stratified separately for each target.
  • Tuning: nested CV (outer 5 × 3, inner 3 × 2) with Optuna TPE, 10 trials per outer fold, so reported development scores are not tuned on the folds they are measured on.
  • After the holdout (Notebooks 7–8): development data only, nested CV. Calibration is monotone, so the holdout ROC-AUC and PR-AUC still describe the served models.

3Models and evaluation

Model selection

Logistic regression, linear and RBF SVMs, random forest, XGBoost and LightGBM were compared for every target under the same 25 folds and both encodings (Notebooks 3–4). The strongest candidates were tuned in nested CV (Notebook 5) and frozen:

Tree ensembles were preferred over a slightly better-scoring average of many models because they support exact, real-time SHAP (§4). The served version v1.1 adds Platt calibration fitted on the development out-of-fold predictions and pre-declared operating thresholds: for Cath the highest threshold keeping development sensitivity ≥ 0.90 (rule-out safety), for the vessels Youden's J. Each pipeline's SHA-256 is checked against the release manifest when the service starts.

Can the models get better?

A development-only search of ~30 candidates (ensembles, stacking, MLP, TabPFN v2 transformer), paired on the same 25 folds with a corrected t-test, found at most +0.01–0.02 ROC-AUC, none of it statistically significant. With 242 development patients, data, not modelling, is the limit; the interpretable shipped models were kept.

4Explainability, dashboard and 3D pipeline

Explanations (requirement 3b–c)

  • Exact SHAP per request (shap.TreeExplainer on the served pipelines), aggregated from transformed columns back to the 54 clinical inputs.
  • Each attribution carries the patient's raw value, its clinical domain, and its share of the total |SHAP|, so magnitudes are comparable across log-odds (XGBoost) and probability (forest) units.
  • The Explain tab shows a one-sentence summary ("mainly raised by…; lowered by…"), a diverging raise/lower chart, contribution by clinical domain, and a sortable physiological table of every measurement with its value, typical adult range and share. Hovering a bar highlights that input on the form.
  • Global importance per target and the observed stenosis rate per probability band are served by the API and shown in the Evidence tab.
  • Attributions describe model associations, not causes; the UI says so.

Dashboard workflow

  • Inputs: sections with units and search; chips count abnormal findings; chest pain is a single choice and BMI is derived, so contradictory inputs are impossible. Impossible values are rejected with a message; unusual ones are accepted with a warning.
  • Live what-if: every edit re-scores; summary chips show how far each estimate moved (e.g. EF 40 → 60%: overall CAD ▼ 14 points).
  • Threshold tab: presets and a slider move along the development ROC curve; sensitivity, specificity, PPV and NPV update live. Only the flag changes, never the probability.
  • Consistency: a note appears when a vessel estimate exceeds the overall CAD estimate (the four models are independent).

3D pipeline (requirements 2 and 4)

  • Source anatomy: BodyParts3D (DBCLS, CC BY 4.0, FMA-based). tools/build_anatomy.py range-fetches only the ~7 MB of parts it needs from the official archive, crops, simplifies, groups by FMA concept and writes heart.glb (2.0 MB) and thorax.glb (2.5 MB, loaded only for the chest view).
  • Target ↔ mesh correspondence: each model target maps to one mesh group named vessel_<TARGET>: LAD = anterior interventricular branch with diagonal and conus branches; LCX = circumflex branch; RCA = trunk, marginal and posterior interventricular branches. The left main and great vessels stay grey ("not modelled").
  • Muscle surface: BodyParts3D models ventricles only as blood cavities, so the outer wall is reconstructed by growing each cavity by the local wall thickness measured from the coronary arteries; arteries end up a median 0.9 mm from the surface.
  • Colour mapping: one fixed 0–100% ramp with monotone OKLab lightness (order survives colour-vision deficiency) and a numeric legend. The whole system shares one colour because the model predicts stenosis somewhere in the vessel, not a lesion location. Colours ease to new values on every prediction.
  • Interaction: rotate, zoom, pan; six camera presets (anterior, left lateral, inferior, RAO, posterior, chest); hover tooltips; click or keys 1–4 to select; F for full-screen 3D; optional labels; a heartbeat at the patient's entered pulse rate, with optional synthesised heart sounds.
  • Shaders (no post-processing passes): blood-flow pulses per beat, risk glow and halo proportional to probability, a sweep of light when a new prediction arrives. Cost: 1.7 ms per frame at 2400 × 1600 on integrated Intel Arc graphics, far inside the 16.7 ms budget for 60 fps; no dedicated GPU needed. A procedural heart is the fallback if the meshes are missing.

5System architecture and integration

Figure 6. Data flow. Every number in the UI comes from the API; nothing is hard-coded in the frontend.

API

GET /operating-curvesDevelopment sens./spec./PPV/NPV at every threshold

Input schema rejects unknown fields (so outcome labels can never be sent as inputs), impossible combinations (two chest-pain classes, current and ex-smoker, Lymph + Neut > 100) and non-integer codes.

Real-time integration

Inputs are debounced and posted to /predict; one response drives the summary chips, result cards, explanation charts and the 3D colours together, so the model output and the highlighted LAD, LCX and RCA always correspond. Scoring is single-threaded per request (~60 ms with SHAP).

Extensibility

  • New clinical feature: add it to the training data and to config/features.js (label, unit, range, section); the form, validation and explanations pick it up.
  • New prediction target or model: register its pipeline in backend/app/config.py and its calibration in the post-processing file; the registry loads, hash-checks and scores every listed target.
  • New anatomical structure: add an FMA group to build_anatomy.py; the viewer binds any vessel_<TARGET> mesh automatically. Camera views are data in config/anatomy.js.

Engineering quality

  • 39 automated tests (API contracts, leakage rejection, frozen-output regression, calibration monotonicity, SHAP additivity and units, security headers, rate limits); GitHub Actions runs them on every push, then builds and smoke-tests the Docker image.
  • Production hardening: per-response CSP nonce, security headers, request-size limits, per-client rate limiting, request IDs, logs that never contain patient data, non-root container with a health check.
  • Offline-capable frontend: Three.js, GSAP and fonts load from a CDN with integrity hashes and fall back to vendored copies when offline.

6Usage

Python 3.13. From the repository root:

pip install -r requirements-notebooks.txt
uvicorn backend.app.main:app --port 8000

Open http://localhost:8000 (overview) or /app.html (explorer). Or with Docker:

docker build -t coronary-risk-explorer .
docker run -p 8000:8000 coronary-risk-explorer

Using the explorer: load one of five example patients or enter values; watch the estimates, artery colours and explanations update. Click an artery (or press 1–4) to focus it; drag to rotate, scroll to zoom, V cycles views, F full-screen, ? lists shortcuts. Use the Threshold tab to choose how cautious the flags are.

Reproduce the models: run Notebooks 1–8 in order; Notebook 6 verifies it reproduces the original one-time holdout predictions. Tests: python -m pytest backend/tests -q. Rebuild the meshes: python tools/build_anatomy.py.

7Limitations

  • Small, single-centre cohort: 303 patients referred for angiography (CAD prevalence 71%); estimates apply to similar referral populations, not to screening. External validation is needed.
  • Wide holdout intervals: 61 patients; one patient moves sensitivity or specificity by 2–6 points. The v1.1 threshold metrics are development estimates; testing them without bias needs new data.
  • Weaker vessels: LCX and RCA discrimination is moderate (ROC-AUC 0.70–0.73); left main disease is not modelled separately.
  • Spectrum effects: Q waves, wall-motion abnormality and reduced EF can reflect prior infarction, i.e. established disease.
  • Reference anatomy: the heart is one reference (right-dominant) anatomy, not the patient's; colour marks risk for the whole vessel, not a lesion location.
